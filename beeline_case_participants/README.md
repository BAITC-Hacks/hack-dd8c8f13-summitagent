# Агент управления тарифными маркетинговыми кампаниями

Решение кейса **Beeline Tariff Marketing Campaigns**.

> Все данные кейса синтетические и подготовлены организаторами для хакатона
> (см. `PARTICIPANT_GUIDE.md`). Цифры ниже — результаты на локальной мок-среде,
> а не прогноз балла на судействе.

## Кратко

Аналитик маркетинга планирует кампании на следующий месяц: кому из 23 441
абонента предложить сменить тариф, на какой тариф и через какой канал (push,
SMS, реклама, звонок). Кампании «вслепую» часто уходят в минус: часть переходов
заканчивается падением ARPU, а каждый контакт стоит денег.

Агент сам проверяет гипотезы пилотными кампаниями и возвращает готовый план до
10 кампаний, который укладывается в лимиты кейса: бюджет 100 000 у.е.,
15 000 контактов, 20 пилотов.

## Что реализовано

Всё находится в [`agent.py`](agent.py), класс `Agent` с методом `act(env)`:

- **Априорная оценка по истории.** Из `data/change_tariff.csv` строится таблица
  ожидаемого эффекта перехода «тариф A → тариф B» для каждого ARPU-сегмента.
- **Отбор кандидатов.** Пары «текущий тариф + ARPU-сегмент» с аудиторией от 100
  абонентов скрещиваются с историей. Для пилотов берутся 20 лучших
  кандидатов.
- **Двухфазная разведка пилотами.** Сначала дешёвый скрининг на 30 абонентов,
  затем уточнение на 150–200 абонентов для лучших выживших.
- **Учёт надёжности пилота.** Итоговая оценка смешивает историю и пилоты, и вес
  пилотов растёт с числом абонентов в них.
- **Выбор канала с учётом бюджета.** Каждой кампании достаётся канал с лучшим
  чистым результатом на контакт, пока на него хватает бюджета.
- **Соблюдение лимитов.** Не больше 10 кампаний и 5 000 абонентов на кампанию,
  остатки бюджета и контактов учитываются. На одну пару «тариф + сегмент» — одна
  кампания, потому что абонент засчитывается только один раз.
- **Защита от сбоев.** Если внутри `act()` что-то упадёт, агент вернёт лучшие
  кампании из уже найденного, а не пустой список.

## Как работает решение

На вход агент получает объект среды `env`, на выходе возвращает список
кампаний.

1. **История → априорный эффект.** Для каждой группы
   `(tariff_plan_code_from, tariff_plan_code_to, arpu_segment)` считается
   среднее относительное изменение ARPU, `(ARPU после − ARPU до) / ARPU до`,
   обрезанное до [−1, 3]. Его умножают на долю таких переходов (конверсию).
   Средние малых групп стягиваются к нулю:
   `pct × count / (count + 5)`.
2. **Кандидаты.** Из `env.customer_profile` берутся пары «текущий тариф +
   ARPU-сегмент» с аудиторией не меньше 100 и к ним присоединяются целевые
   тарифы из истории. Кандидаты ранжируются по
   `historical_score = априорный эффект × средний predicted_arpu`, и берутся
   20 лучших с положительной оценкой.
3. **Скрининг.** Лучшие кандидаты проходят пилоты на 30 абонентов в самом
   дешёвом канале (`push`). На скрининг уходят все пилоты, кроме 6 последних,
   то есть 14 из 20. Кандидаты с `observed_lift_ratio <= 0` отсеиваются.
4. **Уточнение.** До 6 лучших выживших пар получают пилот на 150–200 абонентов
   в том канале, который агент планирует для финальной кампании. На уточнение
   отводится не больше 25% оставшегося бюджета, поэтому слишком дорогой канал
   заменяется более дешёвым.
5. **Итоговая оценка.** Результат пилота делится на множитель его канала и
   смешивается с историей:
   `оценка = w × пилот + (1 − w) × история`, где `w = n / (n + 50)`, а `n` —
   число абонентов во всех пилотах кандидата.
6. **Канал.** Для каждого канала считается чистый результат на контакт:
   `оценка × conversion_multiplier × средний predicted_arpu − cost_per_contact`.
7. **План.** Кандидаты сортируются по ожидаемому результату кампании. Жадно
   набирается до 10 кампаний, сначала в самом дешёвом канале. Затем каналы
   повышаются в порядке «прирост на единицу затрат», пока позволяет
   `env.remaining_budget`.

Пример кампании в выходном списке:

```python
{"campaign_name": "tariff_4_MID_to_tariff_8",
 "filter_arpu_segment": "MID", "filter_current_tariff": "tariff_4",
 "target_tariff": "tariff_8", "channel": "sms"}
```

## Технологии

- **Язык:** Python. Проверено на Python 3.11.1.
- **Библиотеки:** `pandas`, `numpy`. Проверено на pandas 3.0.1 и numpy 2.4.3.
  Других зависимостей у `agent.py` нет, из стандартной библиотеки используется
  только `pathlib`.
- **AI-модели, LLM, внешние API и сервисы:** не используются. Все решения
  принимаются по историческим данным и результатам пилотов.

## Архитектура проекта

| Файл | Роль |
|---|---|
| `agent.py` | **Наше решение:** класс `Agent`, разведка пилотами и сборка плана |
| `environment.py` | Среда организаторов: `AgentEnvironment` и `run_pilot()` с зашумлённым результатом. Модель эффектов скрыта в замыкании |
| `mock_environment.py` | Локальная мок-среда: модель эффектов — простое усреднение `data/change_tariff.csv` |
| `scoring_core.py` | Подсчёт результата: лимиты, бюджет, дедупликация абонентов, чистый результат. Тот же код, что на судействе |
| `local_eval.py` | Локальная проверка: запускает агента на мок-среде и печатает отчёт |
| `make_submission.py` | Запускает агента с seed 42 и сохраняет `submission.csv` |
| `agent_template.py` | Шаблон от организаторов, в решении не используется |

Взаимодействие компонентов:

```
local_eval.py / make_submission.py
        │  make_mock_env(seed)
        ▼
mock_environment.py ──► environment.py (AgentEnvironment + run_pilot)
                                │ env
                                ▼
                        agent.py: Agent.act(env)
                          ├─ data/change_tariff.csv → априорный эффект
                          ├─ env.run_pilot(...) × 20 → наблюдаемые эффекты
                          └─ список до 10 кампаний
                                │
                                ▼
                scoring_core.py: score_campaigns(пилоты + кампании)
                                │
                                ▼
                  отчёт / submission.csv
```

Пилотные контакты — это реальные контакты: они тоже тратят бюджет и охват и
идут в общий зачёт вместе с финальными кампаниями.

## Установка и запуск

1. Установите Python 3.11 или новее и зависимости:

   ```bash
   pip install pandas numpy
   ```

2. Перейдите в папку проекта. Скрипты читают `data/` и `customer_profile.csv`
   по относительным путям, поэтому запускать их нужно отсюда:

   ```bash
   cd beeline_case_participants
   ```

3. Один прогон с подробным отчётом (seed 42):

   ```bash
   python local_eval.py
   ```

4. Проверка устойчивости на 10 разных seed:

   ```bash
   python local_eval.py --runs 10
   ```

5. Генерация файла для сдачи:

   ```bash
   python make_submission.py
   ```

В консоли Windows кириллица может выводиться неправильно. В таком случае
перед запуском задайте `PYTHONIOENCODING=utf-8`.

## Как проверить решение

**Шаг 1.** Запустите `python local_eval.py` и проверьте в выводе:

- `Статус: PASS` и положительный `ЧИСТЫЙ РЕЗУЛЬТАТ (net)`;
- `Пилотов проведено: 20 из 20`, агент использует пилоты;
- нет строк «Кампания … отброшена», все 10 кампаний корректны;
- бюджет не превышает 100 000 у.е.;
- в блоке «По кампаниям» сначала идут 20 пилотов (`pilot_1` … `pilot_20`):
  14 скрининговых в `push` на 30 абонентов и 6 уточняющих на 150–200. За ними
  идут финальные кампании.

Наш результат на seed 42: чистый результат **+4 409 421** (+2,927% к baseline
150 641 084). В плане 10 кампаний, 8 в `digital_ads` и 2 в `sms`; затраты
97 632 у.е. из 100 000.

**Шаг 2.** Запустите `python local_eval.py --runs 10` и посмотрите на строку
`прогонов в плюс`. Наш результат: **10 из 10**, медиана +4 167 162, минимум
+3 698 604, максимум +4 814 904. Знак результата между seed не меняется.

**Шаг 3.** Запустите `python make_submission.py` дважды. Агент не использует
случайность, поэтому `submission.csv` получается одинаковым при каждом запуске.

## Данные и интеграции

| Файл | Как используется |
|---|---|
| `data/change_tariff.csv` | **Агент:** история смен тарифа. Из неё строится априорный эффект (`AVG_ARPU_PREV_3M`, `AVG_ARPU_NEXT_3M`, `tariff_plan_code_from/to`). Мок-среда строит из этого же файла свою модель эффектов |
| `customer_profile.csv` | Аудитория, передаётся агенту как `env.customer_profile`. Агент использует `ID_NUMBER`, `current_tariff`, `arpu_segment`, `predicted_arpu` |
| `data/dict_tariff.csv` | Справочник тарифов, передаётся как `env.tariffs`. Агент проверяет по нему существование тарифов, а `price_tariff` берёт только в резервном режиме без истории |
| `data/traffic.csv`, `data/arpu_monthly.csv` | Не используются |
| `tariff_dictionary.csv`, `feature_dictionary.csv` | Справочные описания, в коде не используются |

Внешних интеграций нет: агент работает офлайн и обращается только к объекту
`env` и к файлу `data/change_tariff.csv`. Файл ищется рядом с `agent.py`, а
затем в текущей папке. Если его нет, агент строит кандидатов из апселла на
более дорогие тарифы с нулевой априорной оценкой, и решения принимаются
только по пилотам.

## Ограничения

- **LLM не используется.** Пункт «LLM в контуре принятия решений» из
  опциональных требований не реализован.
- **Результат на судействе будет другим.** На мок-среде эффекты взяты из той
  же истории, что и априорная оценка агента, поэтому локальные цифры
  оптимистичны. На судействе эффекты другие, и там всё решают пилоты.
- **Половина охвата не используется.** Вместе с пилотами агент контактирует
  около 6,7 тыс. абонентов из 15 тыс. доступных. План упирается в лимит в 10 кампаний,
  а каждая кампания нацелена на одну пару «тариф + сегмент». Объединять
  несколько текущих тарифов в одну кампанию (`"tariff_4;tariff_8"`) агент
  не умеет.
- **Фильтры только по ARPU-сегменту и текущему тарифу.** Фильтры
  `filter_data_segment` и `filter_call_segment` не используются.
- **Разведка адаптивна частично.** Число пилотов (14 + 6), их размеры (30 и
  150–200), вес `n / (n + 50)` и доля бюджета на уточнение (25%) заданы
  константами. Адаптивны выбор кандидатов для уточнения и канал уточняющего
  пилота.
- **Пилотных абонентов контактируют повторно.** Финальная кампания на ту же
  пару снова включает абонентов из пилота и платит за них ещё раз, хотя эффект
  засчитывается один раз.
- **Данные о потреблении не используются.** Файлы `traffic.csv` и
  `arpu_monthly.csv`, а также поведенческие колонки профиля в решении не
  участвуют.
- **Нет `requirements.txt`.** Достаточно `pandas` и `numpy`, которые нужны и
  самой среде организаторов.
